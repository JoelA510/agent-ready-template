# Accessibility

Unlike **Foundations → Colors**, this page is not an options menu. Color strategy is a
genuine, undecided fork with real trade-offs on both sides; accessibility is not that kind
of question. Every component in this system must meet **WCAG 2.2 Level AA**, full stop.
There's no version of "recommendation vs. alternative" here worth presenting, because there
is no credible argument for shipping a lower bar to real users — some of whom will be
using assistive technology, low-vision, colorblind, or simply tired and looking at a screen
in bad light. That's not a hypothetical population; it's most people, some of the time.

## The baseline: AA, not AAA, and not less

WCAG 2.2 AA is the floor for every component in this library — not an aspiration to work
toward, not a stretch goal, the actual minimum bar a component has to clear to be considered
done (see **Introduction**, "What done looks like for a component," point 4).

It's worth explaining why the target is AA and not the stricter AAA level, since "more
accessible" sounds like it should always be better. AAA's normal-text contrast requirement
is 7:1, against AA's 4.5:1. In practice, 7:1 is genuinely hard to hit with any brand color
that has real personality — pushed far enough to clear 7:1, most colorful brand identities
get desaturated into near-grayscale, because chroma and contrast trade off against each
other at a fixed lightness. Mandating AAA sitewide would mean either giving up the placeholder brand color as a UI color entirely, or using it only in illustrative,
non-text contexts. AA at 4.5:1 is the level where real brand personality and rigorous
accessibility both fit in the same palette — which is the pragmatic reason nearly every
mature design system (GOV.UK included) targets AA as its baseline and treats AAA as a
bonus where it falls out naturally, not as the universal mandate.

And in this system's case, hitting AA isn't a bare-minimum scrape. The primary color pairing
— white text on `brand-700` — measures **6.73:1**. AA's normal-text floor is 4.5:1; AAA's is
7:1. At 6.73:1 this pairing is most of the way to AAA already, well clear of AA with real
margin to spare. Meeting the AA baseline here didn't require trading away brand color for
compliance — see **Foundations → Colors** for the full contrast breakdown behind that number.
Because that number is measured against the placeholder palette, re-measure this pairing once
you swap in your organization's brand ramp and verify it still clears AA.

  <div className="text-center">
    <div className="flex items-center justify-center size-20 rounded-md bg-brand-700">
      <span className="text-white text-sm font-medium">Aa</span>
    </div>
    <p className="text-xs mt-1 font-mono">6.73:1</p>
    <p className="text-xs text-neutral-500">white on brand-700</p>
  </div>

</div>

## Contrast, concretely

Every semantic color pairing this system ships — in both the light and dark theme — has
been checked against measured contrast ratios, not eyeballed. These are the verified
numbers for the pairings used most heavily across components:

| Pairing | Ratio | Passes |
| --- | --- | --- |
| `primary-foreground` on `primary` (light) | 6.73:1 | AA ✓ (just under the 7:1 AAA-normal threshold) |
| `foreground` on `background` (light) | 17.5:1 | AAA ✓ |
| `muted-foreground` on `background` (light) | 5.33:1 | AA normal text ✓ |
| `accent-foreground` on `accent` (light) | 10.2:1 | AAA ✓ |
| `foreground` on `background` (dark) | 17.5:1 | AAA ✓ |

A few things worth noting about that table. First, `muted-foreground` — the pairing used
for secondary and de-emphasized text, the kind of text most likely to get pushed too light
in the name of visual hierarchy — clears AA (4.5:1) at 5.33:1 on the page. Its tightest real
surface is a highlighted menu or select item (`bg-accent`), where it measures 4.52:1 — which
is why `palette.neutral.600` sits where it does. Second, `foreground` on `background` measures identically at 17.5:1 in both
light and dark theme; the dark theme isn't a lower-effort inversion, it's held to the same
standard as light.

One pairing deserves a specific callout: **warning uses dark text, not white, on its amber
background.** `warning-foreground` resolves to `neutral-950` rather than `color.white` in
both themes. This is deliberate, not an oversight — amber and yellow backgrounds are a
notoriously common way to accidentally fail contrast, because white text on a mid-value
amber routinely lands somewhere in the 2:1–3:1 range, well under the 4.5:1 floor, and it's
an easy trap to fall into because white-on-color is the reflexive default for every other
status role in the light theme (`destructive`, `success`, `info` all use white foregrounds
there because their backgrounds are dark enough to support it). Warning's background isn't
dark enough for that pattern, so it breaks it on purpose:

<div className="flex flex-wrap items-center gap-4 my-4">
  <span className="inline-flex items-center rounded-md bg-warning px-3 py-1.5 text-sm font-medium text-warning-foreground">
    Needs attention
  </span>
  <span className="text-xs text-neutral-500">warning-foreground (neutral-950) on warning</span>
</div>

In the dark theme every status role follows the same pattern as `primary` and `warning`: a
light fill (the `300` step) with `neutral-950` text. That's forced by the other way the
components use these roles — as **text** on the page. A form error is `text-destructive` on
`background`, and a destructive menu item is `text-destructive` on `popover`; a red dark
enough to carry white text measured 2.9:1 as text on the dark card surface, well under the
bar.

If you're adding a new status color or a new tint of an existing one, don't assume white
foreground is safe — check it, especially for anything in the yellow/amber/lime range.

### What the contrast gate checks

`npm run check-contrast` (part of `npm run check`) recomputes every ratio from the token
source, so none of the numbers above can quietly go stale after a palette swap. It checks
three sets of pairings in both themes:

- **Derived from token names:** every `X-foreground` on `X`, plus `foreground` on
  `background`.
- **Declared from component usage:** every role a component renders as text on a surface
  other than its own — `muted-foreground` on a highlighted `accent` item, `destructive` on the
  page and inside popovers, alert text on each status tint (translucent tints are composited
  before measuring). These live in `TEXT_ON_SURFACE` in `scripts/check-contrast.mjs`.
- **Non-text (3:1):** focus rings, at the opacity the components draw them, and the
  status-colored alert icons against their tint.

The declared list is only as good as its coverage, so the script also scans
`src/components/` (stories included) for every text, icon, and focus-ring color class, in
every Tailwind spelling (`text-x/70`, `text-x!`, `text-(--x)`, …), and fails when:

- a role is used as text (or an icon color) at an opacity no pairing measures — adding
  `text-warning` or `text-muted-foreground/60` without declaring where it lands fails the gate;
- a single class list sets both an element's text and its own background (`bg-primary/90
  text-primary-foreground`) and that exact combination isn't measured.

What it can't see: text whose background comes from an *ancestor* element. Those pairings are
covered per role — the role must be measured on some surface — so when you put an existing
text role on a new kind of surface, add that surface to `TEXT_ON_SURFACE` yourself.

## Keyboard and focus

Every interactive primitive in this library must be fully operable by keyboard alone: tab
to it, activate it, escape or dismiss it, without ever touching a mouse or trackpad. For
most of what's here, this falls out of building on [Radix
primitives](https://www.radix-ui.com/primitives) rather than hand-rolled interactive
markup — Radix's `Tabs` and `Select` implement roving `tabindex` so arrow keys move focus
correctly within the group, and `Dialog` implements focus trapping (focus can't escape the
dialog to the page behind it) plus Escape-to-close, out of the box.

That inheritance is a head start, not a guarantee. It's still the contributor's job to
verify keyboard behavior on every new component and every meaningful new state, never to
assume "it's built on Radix, so it's fine." A composed pattern can still break keyboard
flow in ways no primitive would catch on its own — a custom `onKeyDown` handler that
swallows Tab, a focus target that isn't actually focusable, an icon-only button with no
accessible name.

The other half of keyboard support is making focus *visible*, not just present. Every
focusable element in this system carries the shared focus ring pattern:

```
outline-none focus-visible:ring-3 focus-visible:ring-ring focus-visible:border-ring
```

This appears verbatim across `Button`, `Input`, `Textarea`, `Checkbox`, `Switch`, `Select`,
and `Badge`. The ring is drawn at **full opacity** on purpose. The shadcn convention this
system started from is a translucent `ring-ring/50` halo, and at 50% the light theme's ring
measured 1.82:1 against the page — under the 3:1 that SC 1.4.11 asks of a focus indicator,
and on a borderless `ghost` or `link` button the ring is the only indicator there is. The
contrast gate reads the opacity from the components' `ring-ring/<n>` classes, so bringing the
halo back fails `npm run check` unless the palette can carry it.

The rule more important than the specific class names: **never remove a
focus outline without putting an equally visible replacement in its place.** `outline-none`
only appears in this codebase paired with a `focus-visible:ring-*` replacement on the same
element — never on its own. A component with focus removed and nothing standing in for it
is invisible to anyone tabbing through the page, which is a keyboard user's entire mental
model of where they are.

## What WCAG 2.2 added, and what checks it

WCAG 2.2 (a W3C Recommendation since October 2023) keeps every 2.1 criterion except 4.1.1
Parsing, which it made obsolete, and adds six at A and AA. Most of them can't be seen by
`axe` in jsdom, which has no layout; `npm run test:browser` runs axe over every story in real
Chromium, which sees some of them. This table says honestly how each is held.

| Criterion | What it asks | How it's held here |
| --- | --- | --- |
| 2.4.11 Focus Not Obscured (Minimum), AA | A focused control isn't entirely hidden behind author content (sticky headers, toasts, banners). | Modal components trap focus inside themselves, but that doesn't stop something drawn above them. **Toasts are:** the `Toaster` sits above every modal (`--z-toast` is the top of the z-index scale), so a toast raised from a `Drawer` or `Dialog` can land on its footer buttons. Place the `Toaster` where your modals' actions aren't (a bottom sheet's actions are at the bottom), and tab through each page with a toast and any sticky header showing. Manual. |
| 2.5.7 Dragging Movements, AA | Anything done by dragging can also be done with a single pointer, without dragging. | `Slider` sets a value from a click on the track; `Carousel` has previous/next buttons; `Drawer` closes from its overlay and buttons; a toast, which Sonner dismisses by swipe, has a close button (the `Toaster` turns it on by default; `wcag22.test.tsx` holds it there). **`Resizable` doesn't:** its handle resizes by drag or keyboard only. If you ship it, add a single-pointer way to change the layout (collapse/expand buttons, preset sizes). |
| 2.5.8 Target Size (Minimum), AA | Pointer targets are at least 24 by 24 CSS pixels, or spaced so a 24px circle around each touches no other target. | Gated per story in Chromium (see below). Under 24px, and passing only through the spacing rule, so the consuming app's layout decides: `Checkbox` and `RadioGroup` items (16px), the `Switch` (20px tall), the `Slider` thumb (16px), and the `Dialog` and `Sheet` close buttons (16px). Keep their centers at least 24px from any other target (for 16px controls, `gap-2` or more). `SidebarMenuAction` and `SidebarGroupAction` sit on top of another target, where spacing can't help, so they're 24px. |
| 3.2.6 Consistent Help, A | Help mechanisms appear in the same place on every page. | App-level; nothing a component can guarantee. |
| 3.3.7 Redundant Entry, A | Information already entered in a process isn't asked for again. | App-level; nothing a component can guarantee. |
| 3.3.8 Accessible Authentication (Minimum), AA | Signing in doesn't depend on a cognitive test such as remembering or transcribing. | `Input` doesn't block paste or autofill. `InputOTP` accepts a pasted code as it arrives in an email or SMS: with a `pattern`, input-otp drops a paste that doesn't match, so the wrapper strips spaces and hyphens first (`123-456` pastes as `123456`; `wcag22.test.tsx`). Keep it that way: never add an `onPaste` block, and never turn off `autocomplete` on a credential or code field. |

**Target size, gated:** `npm run test:browser` runs every story in Chromium, once in the light
theme and once in the dark, with axe after it renders, `target-size` included (axe ships that
rule off; `.storybook/preview.tsx` turns it on), and fails on any violation; CI runs it on every
pull request. A canary story fails the run if the stories ever render without the design
system's CSS, or in the wrong theme, which would make every size and contrast measurement
meaningless. A story that needs an exception to one rule says why beside it, and
`stories.a11y.test.tsx` fails until the exception is added to its reviewed list; no story can
turn `target-size` off. What it can't see: a menu's, dialog's, or popover's contents unless a
story renders them open. A one-time measurement (executed 2026-09-24) also opened the first
trigger in each of 34 stories: 543 targets, none failing, and one it couldn't decide, the
`Sidebar` rail, a 16px strip with `tabindex="-1"` that does what `SidebarTrigger` does (WCAG's
"equivalent" exception). Repeat that by hand when you change what an overlay contains.

## Motion

Motion has its own accessibility surface — vestibular disorders and motion sensitivity are
real, common, and easy to trigger with careless animation. Rather than duplicate that
guidance here, see **Foundations → Elevation & Motion** for the full reduced-motion
approach (respecting `prefers-reduced-motion`, which transitions are safe to keep versus
which need a reduced/no-motion fallback).

## What to check before shipping a new component

A practical checklist, not a formal audit — most of this takes a few minutes per
component, and skipping it is how regressions get shipped instead of caught:

1. **Keyboard-only walkthrough.** Unplug the mouse, mentally or literally. Tab to the
   component, through every interactive state, and back out. Verify you can reach it,
   operate it, and leave it — including closing anything modal — without a pointer. Where
   reaching it or seeing its focus indicator is the risk, keep the walkthrough as a story's
   play test, as `ScrollArea`'s stories do; the browser tier runs it on every change.
2. **Screen reader smoke test.** Run it once with VoiceOver (macOS) or NVDA (Windows).
   You're listening for whether the component's name, role, and state are announced
   sensibly — not doing a full audit, just catching the "this button has no accessible
   name" class of bug before it ships.
3. **Contrast check for any new color pairing.** If a component introduces a color
   combination not already in the tables on this page or in **Foundations → Colors**,
   measure it and record the ratio. Don't assume a pairing is fine because it "looks dark
   enough" — the warning-color case above is exactly the kind of pairing that looks fine
   and isn't.
4. **Storybook's a11y addon panel shows no violations.** This Storybook instance already
   runs `axe-core` automatically against every story via the accessibility addon — open the
   Accessibility panel for each new story and verify it's clean before calling the
   component done, in both themes (the toolbar's theme switch). The panel runs in a real
   browser, so it sees what jsdom can't (rendered contrast, target size), and
   `npm run test:browser` runs the same checks in both themes as a gate, which CI enforces. A
   red violation in the panel is a failing test.
5. **The WCAG 2.2 additions** in the table above: anything draggable has a single-pointer
   alternative, small targets are spaced, and nothing sticky can cover a focused control.

None of these five replace each other — axe-core catches a wide class of programmatically
detectable issues (missing labels, insufficient contrast, invalid ARIA) but it can't tell
you whether tab order is sensible or whether a screen reader announcement actually makes
sense out loud. All five are cheap enough to run on every new component that skipping one
is rarely a real time save.

For accessibility on the content and writing side — alt text, link text that makes sense
out of context, heading structure — see **Brand & Content → Accessibility in Writing**
rather than this page.
