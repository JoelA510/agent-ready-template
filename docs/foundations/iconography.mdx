# Iconography

This is one of the shortest foundations pages in this system, and that's intentional — there
isn't a genuine three-way fork to weigh here the way there is for color or typography. One
icon library, used consistently, is close to a structural requirement rather than a stylistic
preference. What's below is settled and safe to build against today.

## One icon set: Lucide

[`lucide-react`](https://lucide.dev/) is already an installed dependency
(`lucide-react` in `package.json`) and is the only icon source this system uses. That's not a
new choice this system is introducing — it's continuity with what Acme already
ships: Acme's production app, `acme-analytics` (a Next.js analytics and billing
dashboard), uses Lucide too. Adopting it here means
an icon that appears in this Storybook and one that appears in that dashboard are, in the
cases where both use the same icon name, drawn from the identical source — same stroke width,
same corner treatment, same visual weight.

## Why one library counts more than which one

Lucide isn't recommended here because it's objectively superior to every other icon set —
Heroicons, Phosphor, and Feather are all reasonable, well-maintained alternatives with a
similar outlined, single-weight aesthetic. It's recommended because **mixing icon sources is
one of the fastest ways to make a well-built interface read as sloppy**, and that damage
happens even when every individual icon looks fine in isolation. Two icon sets almost never
share the exact same stroke width, corner radius, or optical sizing — one set's "20px" icon
sits on a slightly different visual baseline than another's. Side by side in a toolbar, that
shows up as a faint but real inconsistency that most users can't name but do notice, the same
way two slightly different blues next to each other read as a mistake even if neither blue is
wrong on its own. The fix isn't picking a better icon set — it's picking one and not
deviating, which is a simpler bar to hold a whole team to than "use good taste when mixing
icon styles."

## Sizing convention

| Class | Size | Use it for |
| --- | --- | --- |
| `size-4` | 16px | The default. Icons inline with text (a link with a trailing arrow), and icons inside buttons alongside a label. |
| `size-5` | 20px | Slightly more prominent standalone icons — an icon-only button that's a primary action, a nav item's icon when there's no adjacent label. |
| `size-6` and up | 24px+ | Genuinely large or decorative use only — an empty-state illustration, a large status icon on its own. Not for anything sitting next to text. |

As with spacing, these three steps are guidance for the common cases, not an exhaustive
enum — an icon sitting in an unusual layout can reasonably use an in-between size, but the
default reflex for "icon next to text" should be `size-4` without needing to think about it.

## Accessibility: the rule is about whether text is present, not about the icon itself

The same icon can be either purely decorative or the sole label for a control, and which one
it is changes what markup it needs. The rule is simple and has no real exceptions:

- **An icon paired with visible text is decorative.** The text already carries the meaning;
  the icon is reinforcement. It should be hidden from assistive technology
  (`aria-hidden="true"`) so a screen reader doesn't announce redundant or confusing filler —
  it should never get its own `aria-label` in this case.

  ```jsx
  <button>
    <FileText className="size-4" aria-hidden="true" />
    View report
  </button>
  ```

- **An icon used alone as a control — no visible text at all — must have an `aria-label`
  describing the action the button performs, not the icon's appearance.**

  ```jsx
  {/* Correct: describes what happens */}
  <button aria-label="Close dialog">
    <X className="size-4" />
  </button>

  {/* Wrong: describes the icon, not the action — tells a screen reader user
      nothing about what pressing the button does */}
  <button aria-label="X icon">
    <X className="size-4" />
  </button>
  ```

The test to apply when reviewing a component: cover the icon with your hand and read only
what's left. If there's visible text left over that says what the control does, the icon is
decorative and gets `aria-hidden`. If there's nothing left — the icon *is* the entire visible
control — it needs an `aria-label` that names the action a sighted user would infer from
context (what the button does), never a description of the glyph itself.

## Icon-to-meaning pairings

This system doesn't prescribe an exhaustive icon dictionary — that's more rulebook than a
design system needs, and it invites arguments over edge cases better resolved case by case.
A few pairings are worth naming because they map directly onto common product concepts and are
worth reusing consistently rather than reinventing per feature:

| Icon | Typical meaning here |
| --- | --- |
| `FileText` | A document or record — a report, a contract, a billing summary. |
| `Users` | A customer or contact — a customer record, a team/contact list, a project's assigned members. |
| `Calendar` | A deadline or scheduled date — a due date, a renewal deadline, a meeting. |
| `ShieldCheck` | A compliance or governance item — a completed review, a verified/approved status, a governance checklist item. |

Reusing these consistently across the customer portal, internal tools, and any future surface
means a user who learns "the calendar icon means an important date" in one product context
doesn't have to relearn it in another.

## Reference systems this leans on

- **Acme's own `acme-analytics` app** — the strongest reference here isn't an
  external design system, it's Acme's own production dashboard already shipping
  Lucide. This page documents continuity with a real, running product rather than proposing
  something net-new.
- **GOV.UK Design System** — GOV.UK's icon guidance is deliberately minimal and mostly about
  restraint (use icons sparingly, never as the sole means of conveying information); the
  accessibility framing above follows that same instinct.
