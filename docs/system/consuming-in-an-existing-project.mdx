# Consuming this system in an existing project

This template is built to be **forked** — you take the whole repo and it becomes your
organization's design system. That's the happy path, and everything else in this Storybook
assumes it. But sometimes you already have an app and just want to pull pieces of this system
into it. This page is about that case, and about being honest about what it costs.

There is no npm package to install. This is a source template, not a published library
(`package.json` is `private`). So "consuming" it means moving source into your project — and
the components only work once the substrate underneath them exists.

## What every component depends on

A component file like `src/components/ui/button.tsx` looks self-contained, but it leans on a
whole layer beneath it. Copying `button.tsx` into an app that doesn't have this layer gets you
an unstyled or broken button. The substrate:

1. **The design tokens as CSS variables.** Components reference semantic roles (`bg-primary`,
   `text-muted-foreground`, `border-input`). Those resolve to CSS custom properties generated
   from `tokens/**/*.json` into `src/styles/tokens/*.css`. Without them, the classes point at
   nothing.
2. **Tailwind CSS v4, configured CSS-first.** There is no `tailwind.config.js`. The theme is
   wired in `src/styles/globals.css` via `@theme inline`, which maps the generated token
   variables into Tailwind's `--color-*` / `--radius-*` / `--shadow-*` namespaces so
   `bg-primary` and friends compile. You need Tailwind v4 and that `@theme` bridge.
3. **`tw-animate-css`** — supplies the `animate-in` / `animate-out` utilities the overlay
   components (Dialog, Sheet, Popover, menus, Tooltip) use for open/close motion. Without it
   those transitions compile to nothing.
4. **The `cn()` utility** (`src/lib/utils.ts`) and the `@/` path alias that every component
   imports through.
5. **The relevant Radix packages** for interactive components (each `@radix-ui/react-*` the
   component imports), plus `class-variance-authority` for variants.
6. **Class-based dark mode** — the `dark` variant is declared in `globals.css`
   (`@custom-variant dark`), and dark tokens live under a `.dark` selector.

## Two honest paths, plus a shortcut for the components

### Path C — Install components from the registry (the shortcut)

This template ships a **shadcn-compatible registry** (`registry.json` at the repo root, plus
per-component files under `public/r/`, regenerated by `npm run registry:build`). The Pages
workflow (`.github/workflows/pages.yml`) publishes it with this Storybook, at `r/` under the
site's URL, which is `package.json`'s `homepage`. A consuming project pulls a component, with
its npm dependencies and its cross-component dependencies resolved automatically, with one
command:

```bash
npx shadcn@latest add https://<owner>.github.io/<repo>/r/button.json
```

Each item carries its source, and names the components it depends on by their URLs on the same
site, so a dependency always comes from this registry rather than from shadcn's own. That's why
the site has to be at the `homepage` the registry was built for; the workflow won't deploy it
anywhere else.

Each npm dependency is named with the major this template uses (`@tanstack/react-table@^9`),
because a bare name installs npm's latest release, which can be a major the component doesn't
compile against. The CLI installs a named major even when your project already declares that
package, so adding a component moves your project onto that major. If you're on a newer one,
check the diff to `package.json` after `shadcn add`.

That copies `button.tsx` (and, say, `command` + `popover` + `utils` for the combobox) into the
consumer's project and installs the needed npm packages. **It does not install the substrate**,
though — the tokens, the `@theme` bridge, `tw-animate-css`, and class-based dark mode from the
list above still have to exist first, or the copied component renders unstyled. So the registry
automates the *file and dependency* copying in **Path B step 5**; you still do steps 1–4 once.
Use it when you want specific components in an existing app without forking the whole template.

### Path A — Fork, and build your existing app's screens inside it (recommended)

If the existing project is early enough, or you're consolidating onto one front-end, the
lowest-friction option is still to fork this template and bring your app code into it, rather
than the reverse. You inherit the whole substrate, the token pipeline, the docs, and the
`check` gate for free. Everything in this Storybook applies as written.

### Path B — Graft the system onto the existing app

If forking isn't realistic, replicate the substrate in your app first, then bring components
over:

1. **Adopt Tailwind v4** in your app if it isn't already there.
2. **Copy the token source and pipeline:** `tokens/`, `style-dictionary.config.mjs`, and the
   `tokens:build` script. Run it to generate your CSS variables (and, if you have native or
   RN clients, the `platforms/` outputs — see the **Platform outputs** section of the README).
3. **Copy `src/styles/globals.css`** (the `@theme inline` bridge, the `dark` variant, and the
   generated-token imports) into your app's global stylesheet, and import the generated token
   CSS. Add `tw-animate-css`.
4. **Copy `src/lib/utils.ts`** and configure the `@/` path alias (see `tsconfig.app.json` and
   `vite.config.ts` for how it's set here).
5. **Then copy components** from `src/components/ui/` one at a time, installing each one's
   Radix dependency as you go. Bring the co-located `*.stories.tsx` too if you run Storybook —
   it's the usage example.

The order matters: substrate first (steps 1–4), components last (step 5). A component copied in
before its substrate exists will look broken, and it won't be the component's fault.

## What travels cleanly on its own

The **design tokens** are the most portable artifact here. If all you want is a shared visual
language — not the React components — take `tokens/` plus the generated `platforms/` outputs
(typed TS/JSON for web, plus `tokens-native` with the React Native shapes of easing, shadows,
fonts, and line heights; Swift for iOS; XML for Android) and consume those
directly. They carry no framework assumptions. The **written brand & content guide**
(`docs/brand/`) is just as portable — it's prose, and applies regardless of your stack.
